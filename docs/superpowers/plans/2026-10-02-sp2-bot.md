### Task 1: Core play enumeration (`tavli_core`)

**Files:** `packages/tavli_core/lib/src/play/play.dart` (new), `play_tree.dart` (add methods), `lib/src/play/cascade_walker.dart` (new), barrel exports; tests `test/play/plays_test.dart`, `test/play/cascade_walker_test.dart`

**API (binding):**

```dart
class Play {
  final Position finalPosition;
  final List<Step> steps;   // unmodifiable; one canonical legal path
  const Play(this.finalPosition, this.steps);
}

extension on PlayTree (or methods on PlayTree):
  List<Play> plays();                    // eager trees only; one per final; StateError if isLazy
  List<Step>? pathTo(Position finalPos); // eager and lazy; null if not a legal final

class CascadeWalker {
  CascadeWalker(PlayTree tree);          // requires tree.isLazy
  List<Play> sampleCompletions(int n, Random rng); // ≤ n distinct finals, each a complete legal play
  Play greedyCompletion(double Function(BoardView p) score); // at each node pick child maximizing score(child position)
}
```

**Notes:**
- `plays()` order is deterministic: by first discovery in the DFS over `nextSteps`.
- A sampled completion walks random `nextSteps` until `isComplete`. Deduplicate by final; stop after `n` distinct finals or `4n` walks.

**Steps:**
- [ ] Tests first:
  1. For every variant, 20 `randomReachablePositions` × 21 rolls (normal trees):
     - `plays().length == finals.length`;
     - for each play, applying `steps` through `StepRules` from the tree's start reproduces `finalPosition`;
     - `pathTo(final)` is non-null and is a legal path;
     - `pathTo` of a non-final position is null.
  2. Lazy cascade trees: `plays()` throws `StateError`. On 5 small cascade cases, `pathTo` works for every enumerated final (`enumerateFinals`).
  3. `sampleCompletions(8)` returns complete, distinct, legal plays (walk the tree with the steps). The same seed gives the same result.
  4. `greedyCompletion` with a score that prefers a fixed position property (e.g. a lower own pip count) returns a complete legal play whose final maximizes the score among its siblings at each step.
- [ ] Implement, verify core, commit `"tavli_core: play enumeration (plays, pathTo, CascadeWalker)"`.

### Task 3: Evaluator interface, features and race evaluator

**Files:** `lib/src/eval/{evaluator.dart, features.dart, race_eval.dart}`; tests `test/eval/{features_test,race_eval_test,symmetry_test}.dart`

**API:**

```dart
class EvalResult {
  final double winProb, gammonProb, lossGammonProb;
  double get equity => (2 * winProb - 1) + (gammonProb - lossGammonProb);
}

abstract interface class Evaluator {
  EvalResult evaluate(BoardView p, Side me, VariantRules r);
}

bool isRace(BoardView p, VariantRules r);
// No future contact possible: every own checker is past every opponent checker
// along the movement paths. No bar checkers, no pins.

class Features {
  // Computed once per evaluation, from `me`'s perspective.
  // Fields: pipMe, pipOpp, offMe, offOpp, barMe, barOpp,
  //         homePointsMe/Opp, madePointsMe/Opp,
  //         blotsMe/Opp (with shots: direct 1-6, indirect 7-12 count),
  //         primeLenMe/Opp, anchorsMe (points held in opp home),
  //         pinnedMe/Opp, motherPinnedMe/Opp, headCountMe/Opp
}
Features extractFeatures(BoardView p, Side me, VariantRules r);

class RaceEvaluator implements Evaluator { ... }
```

`RaceEvaluator`:
- Effective pip count = pips + wastage, where wastage adds 1 per checker beyond 3 on points 1–3, plus 0.5 per gap in the home board.
- Lead L = `(epcOpp − epcMe) / ((epcMe + epcOpp) / 2)`.
- **Evaluation convention (decided after Task 3 started; binding for all evaluators):** evaluators **ignore who is on roll** and are **exactly antisymmetric**:
  - `evaluate(p, me).equity == −evaluate(p, opp).equity`;
  - `winProb` ↔ `1 − winProb`;
  - `gammonProb` ↔ `lossGammonProb`.
- Callers that need the on-roll effect add it. The cube policy (Task 6) applies a race on-roll shift of −0.04 to the lead of the side **not** on roll. Play selection compares candidates that all have the opponent on roll, so no shift is needed there.
- `winProb = logistic(L * 11)`.
- `gammonProb` = 0 unless `offOpp == 0` and the opponent's bear-in distance is greater than my remaining pips / 8.1; then a logistic of the margin.

**Steps:**
- [ ] Tests first:
  - `isRace`: false at every start; true for a constructed disengaged position in each direction type; false with any checker on the bar or pinned.
  - **Feature counts** on hand-built positions:
    - blots, with direct/indirect shot counts on a position with a known count written in the comment;
    - prime length 4;
    - anchors;
    - pinned and mother-pinned flags.
  - **Race:**
    - equal pip counts give `winProb` in 0.40..0.55;
    - me 20 pips ahead in a 100-pip race gives `winProb > 0.7`;
    - me borne off 14 and the opponent with 15 on its 6-point gives `winProb > 0.95` and `gammonProb > 0.5`.
  - **Symmetry:** for the race evaluator, swapping sides on a mirrored position gives `winProb ≈ 1 − winProb'` (±0.02).
- [ ] Implement, verify, commit `"tavli_bot: evaluator interface, features, race evaluator"`.

### Task 4: Family evaluators and dispatch

**Each family:**
- produces a weighted score *s*;
- maps it as `winProb = logistic(s)`;
- `gammonProb` / `lossGammonProb` come from heuristics on borne-off counts and trapped or behind checkers.

| Family | Terms |
|---|---|
| Hitting | pip lead, blots × shots, home points, prime, anchors, bar |
| Pinning | pinned checkers (opp + / own −, weighted by depth into home), mother safety (big negative when own mother is exposed to pinning), made points, pip lead |

  - **Running:** a 5-point blockade in front of the opponent's head beats scattered points; Long Nard with more checkers off the head (later in the game) is better.

### Task 5: Search (0-ply, 1-ply top-K widening, Expert 2-ply, selection, budget, cascades)

**Files:** `lib/src/search/{search.dart, cascade_search.dart, budget.dart}`; tests `test/search/search_test.dart`, `test/search/tactics_test.dart`

**API:**

```dart
class SearchResult {
  final Play play;
  final double equity;
  final BotStats stats;
}

SearchResult choosePlay({
  required Position position, required Side side, required List<int> dice, required bool cascade,
  required TurnContext context, required VariantRules rules, required LevelProfile profile,
  required Random rng, Evaluator? evaluator, Duration? budget,
  bool Function()? cancelled,
});
```

Semantics: design §5, binding.
- **0-ply value of a play:** `-evaluate(final, opponent).equity`, i.e. from my side with the opponent to roll.
- **1-ply value:** `Σ_roll w(roll) · (−bestOpp(roll))`, where `bestOpp` = max over the opponent's plays of the opponent's 0-ply value of that play. The roll set is the 21 rolls. **Approximation (decided at the Task 5 review):** look-ahead (1-ply and 2-ply) plays every double as four dice, in Gul Bara too: the search does not know the game's roll count, and one cascade tree can take most of a second to build, uninterruptibly. Only the bot's own cascade turn is searched as a cascade (`CascadeWalker`).
- **Budget:** check the deadline between candidates and between rolls. On timeout, use the best fully evaluated candidate at the deepest completed level; `stats.timedOut = true`.
- **Selection noise:** rank the candidates by true equity and keep the best `ceil(n*topFraction)` (≥ 1); then add `(rng.nextDouble()*2-1)*noise` to each kept equity and choose the max. Noise only perturbs the order; no weighted random. The top fraction is applied to the true values (as implemented) because keeping by the noisy values and then taking the max would make it a no-op; this way it bounds how far down the ranking a pick can go.

**Steps:**
- [ ] Tests first:
  1. A single legal play is returned without evaluation (`stats.evaluated == 0`).
  2. Determinism: the same inputs and seed give the same play.
  3. The budget is respected: a stub evaluator that busy-waits 2 ms per call with a 20 ms budget returns within 40 ms with `timedOut` true and a legal play.
  4. Expert with `noise 0` picks the labelled-best play in a tactics suite of at least 12 positions, 4 per family. Examples:
     - hitting: hit a blot to win the race;
     - hitting: make the 5-point with 3-1;
     - pinning: pin the opponent's checker in my home;
     - pinning: avoid exposing the mother;
     - running: build a blockade in front of the opponent's runner;
     - running: Long Nard prefer the head departure;
     - bear-off: safe bear-off vs leaving a shot.

     Each position is hand-built with its expected play and rationale. If Medium also passes it, fine.
  5. Cascade turn: returns a complete legal play on **both** SP1 fixtures, `worstFailingCascade` and `worstCascade` (`packages/tavli_core/benchmark/bench_fixtures.dart`); the budget gate is in Task 9 (sampled p95).
     - `worstCascade` is the expensive one for the walker: about 1 s for `sample(8)` without a stop.
     - Use `sampleCompletions(..., stop:)` with the deadline.
  6. 1-ply is better than 0-ply on at least 2 tactics positions where 0-ply is misled. Construct and document them; if none can be found, document why and drop this test.
- [ ] Implement, verify, commit `"tavli_bot: budgeted search (0/1-ply, expert 2-ply, cascades)"`.

**API:**

```dart
enum StepQuality { best, good, acceptable, poor }

class TurnAnalysis {
  final Map<Step, StepQuality> nextStepQuality;
  final Map<Step, double> nextStepEquity;
  final double bestEquity;        // best play of the turn, from its start
  final double lossSoFar;         // bestEquity − best play still reachable after `steps`
  final double? playEquityLoss;   // when steps form a complete play: best − chosen
}

TurnAnalysis analyzeTurn({
  position, side, dice, cascade, context, rules, steps,
  profile: LevelProfile.of(BotLevel.medium), rng, budget,
});
```

`nextStepEquity[s]` is the best play value (0-ply, or 1-ply within the budget) among plays whose path continues through `steps + [s]`, from the eager `plays()`. Cascades use a greedy completion per next step plus sampled completions. `nextStepQuality` is relative to the best next step, so one next step is always `best` (design §7).

### Task 10: Tournament tool, strength gates and tuning

**Files:** `packages/tavli_bot/tool/tournament.dart` (CLI: `--a medium --b easy --variant portes --games 400 --seed 1 --jobs 8`), `lib/src/tournament/match_runner.dart` (pure, testable); `test/tournament_smoke_test.dart` (40 games, no gate)

**Rules of a tournament game:**
- **Matches:** single games, alternating who opens.
- **Cube:** off.
- **Seeds:** fixed per game.
- **Dice:** from a seeded RNG shared across both bots' games for variance reduction. Play each dice sequence twice with colors swapped; this mirrored-pair design is binding.
- **Scoring:** points scored (gammons count 2, etc.) and win rate.
- **Report:** win rate with a 95 % CI.

**Gates (design §1.4):** families Portes, Plakoto and Fevga, 400 games per pairing.

**Budgets (decided at the Task 10 review, binding):** every gate tournament passes the **desktop-gate budgets** as explicit request budgets (Easy 7 ms, Medium 27 ms, Hard 100 ms, Expert 270 ms; cascades 2×). These approximate the Galaxy S's compute within its device budgets (device targets ÷ 3). The `LevelProfile` device budgets (20/80/300/800 ms) are not used in tournaments: on a desktop Expert would reach 2-ply far more often than on the phone, and the gates would overstate on-device strength. `tool/tournament.dart` defaults to `--budget desktop`.

**Acceptance reading:** a gate's win rate is the point estimate (wins plus half the draws, over 400 games). The 95 % CI is computed over the 200 mirrored pairs (the two games of a pair are not independent). "Expert ≥ Hard within the 95 % CI" means the CI's upper bound is ≥ 50 % (Expert is not significantly worse than Hard).

**Steps:**
- [x] Implement the runner with tests: smoke; mirrored dice pairing; same seed gives the same results.
- Known tuning starting point (Task 3–4 review): blot exposure in `HittingEvaluator` (and the blot/shot terms of `PinningEvaluator`) is about 5–8× under-weighted. Raise those weights first if the hitting gates fail.
- Note: `test/level_test.dart` pins the *initial* `LevelProfile` values. Tuning may change those values; update `level_test` to the tuned values and keep its ordering assertions. This is not "weakening": the gates are the tournaments.
- [x] Run the gate tournaments.
- [x] If a gate fails, tune `LevelProfile` values and evaluator constants and re-run. Record every run (config, results) in the SP2 report's tuning log.
  - Do not loosen a gate.
  - If tuning cannot meet a gate after reasonable effort, stop and report with the data.
- [x] Commit `"tavli_bot: tournament tool + strength gates (results in report)"`.
